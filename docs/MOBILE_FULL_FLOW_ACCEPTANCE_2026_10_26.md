## 阻斷問題 M26-01：日期／時間選擇器互相清理

優先級：**P1，影響主要出攤流程**。在包含日期與時間選擇器的編輯表單中，可遇到時間選擇器消失且無法重新開啟。此場次目前沒有營業時段，管理頁也直接要求先補上時間，因而無法繼續驗收預期現場動線。

### 真實畫面重現

1. 開啟本次新場次 → 編輯 → 展開時間軸。
2. 點「開始營業」，AX 可看到 00～23 小時、00～59 分鐘、確認與取消。
3. 面板存在時量測：DOM `.datetime-picker` 存在，`display: block`，非 inert，附加於 BODY。
4. 實際選取小時後，面板消失；DOM 量測 `pickerCount: 0`、`startValue: ''`，實際 viewport 360×640。
5. 再點該欄位／鍵盤 Enter 無法開啟。取消並重新進入編輯後，可再次看到面板後消失。

部分工具失敗也可能受到彈層消失的影響；本文件不把單次定位器逾時當成 App 缺陷。以下隔離重現另證明了實際程式中的跨實例清理缺陷。

### 程式與隔離證據

- [DateTimePicker](../lib/date-time-picker/DateTimePicker.js)：`destroy()` 呼叫 `cleanupOldElements()`，會刪除頁面上**所有** `.datetime-picker` 與 overlay，而非只清理本實例。
- 另一個時間實例仍持有 `isOpen = true`；其 `open()` 一開始就返回，無法重新建立畫面。
- [DatePicker React 包裝](../components/ui/DatePicker.tsx)：初始化 effect 依賴 `onChange`；[期限欄位](../components/markets/MarketPaymentDeadlineFields.tsx)傳入 inline callback。重繪可造成不相關日期實例 destroy／重建，這是會觸發跨實例清理的路徑；本輪未另加頁面執行追蹤，未斷言每次畫面消失都來自同一個 React 重繪來源。
- 以實際 `DateTimePicker.js` 在隔離 DOM stub 執行：時間實例開啟後有 2 個節點；銷毀另一個未開啟的日期實例後，節點變 0，但時間實例仍標記開啟；再呼叫 open 仍為 0。[重現結果 JSON](ux-evidence/2026-10-26/time-picker-ownership-reproduction.json)。此檢查沒有存取使用者瀏覽器資料。

### 建議修正範圍

1. `destroy()` 只移除自己持有的 picker、overlay 與事件，不掃描刪除其他實例。
2. 若需要同時只能開啟一個挑選器，明確協調前一個 active instance 的 `close()`，同步其狀態，避免只移除 DOM。
3. DatePicker callback 以 ref 維持最新，避免一般重繪重建；日期界限／disabled 變動另有受控更新。非同步初始化補上卸載保護。
4. 針對「A 開啟，B 銷毀」「關閉後立刻重開」「背景同步重繪」「日期與時間互切」補回歸，並重驗原有多選日期與期限。
5. 再續驗錄取 → 繳費 → 開攤 → 現金／非現金成交 → 照片 → 可選現金盤點 → 收攤 → 心得與集中回顧。

以上是修正提案，**本次沒有實作**。涉及瀏覽器 DOM 的挑選器實作與包裝改動仍應遵循 [跨平台規則](CROSS_PLATFORM_VIBE_CODING_GUARDRAILS.md)，不改業務模型或營業／同步寫入規則。

### 修正內容與跨平台邊界

- `lib/date-time-picker/DateTimePicker.js` 僅清理自己擁有的面板、遮罩及延遲工作。開啟另一欄位時明確關閉上一個實例，包含其 `isOpen` 狀態。關閉動畫只移除當次捕捉的舊節點，避免快速重開後被舊計時器刪除。
- 停用與銷毀後不能再開啟；延遲的外部點擊註冊與時間清單捲動會取消。另修正時間清單定位以自身可捲範圍計算，避免平板上已選時間被上緣遮住。
- 三個 React 包裝統一使用 `hooks/useDateTimePicker.ts`：回呼保持最新，普通表單重繪不重建實例；非同步初始化若晚於卸載完成，立即銷毀自己的結果。外部改值、清除、日期界限及 disabled 更新既有實例。
- 平台合約：`lib/platform/contracts/date-time-picker.ts`；resolver：`lib/platform/date-time-picker-capability.ts`；Web adapter：`lib/platform/web/date-time-picker.ts`。CSS 安裝、DOM 目標與既有 vanilla renderer 載入只在 Web adapter；舊 renderer 保留原路徑、由 adapter 封裝，沒有新增原生套件或原生 store adapter。
- 未修改日期／時分選項與保存格式、既有 min/max 規則或金額。DatePicker 補齊 Enter／空白開啟，保留原本欄位 ID、標籤與其他 aria 屬性。

### 雲端與邊界證據

狀態／成交透過 `lib/db/hooks.ts` → `recordEvent` 的本機投影與待送事件 → `lib/sync/sync-push-service.ts` → 雲端事件／投影。現金與心得另走 owner 專用 repository／RPC（`save_market_cash_record`、`save_market_journal`）；現金銷售比較透過 `read_market_cash_sales` 讀來源。

另以現有伺服器設定做**唯讀、限定本次場次與本次商品名稱**的雲端核對，不輸出密鑰、不代替瀏覽器寫入、不讀其他品牌資料。結果：

- `events`：恰有 3 個 `deal_closed`，分別為現金 300、行動支付 200、商品現金 50；商品成交快照成本 20、數量 1，沒有重複成交。
- 市集投影：`total_revenue=550`、`total_profit=530`、`total_deals=3`、`booth_cost=100`。`total_profit` 此處是銷售利潤；畫面估計淨利再扣攤位費為 430。
- `products`：驗收商品 ID `ed7aab5e-75ed-4515-9c6a-097db88b7f02`、stock 9、total_sold 1。
- `market_cash_records`：唯一當日紀錄，第 3 版；開攤總額 1,000，收攤面額 1000×1＋100×3＋50×1＋10×0＝1,350。
- `market_journals`：ID `4e068233-6065-411c-9e7e-789e17c3088a`，整場總結，第 1 版，未移除。
- `sale_photo_evidence`：本場雲端 metadata 0 筆，與上傳在來源檢查即被擋下相符；不宣稱照片已送達。

### 照片待正式環境驗收

本機 `POST /api/sales-photo-evidence/upload` 回傳 403。唯讀 OPTIONS 預檢同一路徑：Origin `http://127.0.0.1:3000` → 403／`cors_origin_denied`；Origin `http://localhost:3000` → 204。路由在驗證／claim 前執行 `createAppApiCorsRejectionResponse`，結果符合本機來源識別／允許來源不一致，不可直接推論正式站也會失敗。

未修改 CORS、放寬任意來源、停用驗證或變更任何雲端權限。正式環境應重新驗證：選取／拍攝 → 預覽確認 → API 成功 → 雲端 metadata 與圖片 → 重載／另一授權裝置可讀 → 本機待送工作正確完成。實體相機及 iOS／Android 權限也尚未驗收。

不帶身分憑證、沒有 request body 的預檢結果另存 [21-cors-preflight-read-only.json](ux-evidence/2026-10-26/21-cors-preflight-read-only.json)。這不是正式環境的測試結果。

本場留下 3 項待補照片：300 元成交保留合成原圖，200 元與 50 元成交選了稍後補、未選圖。既有其他場次的待補工作沒有清除、強制登出或捨棄。
