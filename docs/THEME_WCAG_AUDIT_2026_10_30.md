# 九套預設主題：WCAG 顏色使用與對比分析

> 後續狀態：使用者已同意修正，共用缺口的實作與複驗見 [修正紀錄](THEME_WCAG_FIXES_2026_10_30.md)。本文保留原始修正前分析，以下「尚未實作」為稽核當時狀態。

日期：2026-10-30，Asia/Taipei。**分析而非修正**；本輪未修改應用程式、套用主題、改動個人配色或新增資料。先前配色收斂變更保持原狀。

## 結論與標準範圍

九套主題的現有核心配色檢查都通過；最近新增的選中標籤與外框檢查也通過。但目前不宜標示任何一套為「整個 App 已通過 WCAG」。共用透明度樣式會在 hover、焦點與頁首的實際組合降低對比，現有主題實驗室的五項檢查沒有涵蓋這些情況。

- [WCAG 1.4.1 顏色使用](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)，A：顏色不能是唯一資訊線索，需有可見文字、形狀、圖示或其他區別。此項不能單靠色票數值認證，也不限制 App 只能有幾種顏色。
- [WCAG 1.4.3 最低文字對比](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)，AA：一般文字至少 4.5:1，大字至少 3:1；24 CSS px 一般字或約 18.67 CSS px 粗體屬大字。門檻不以四捨五入後數值判定。
- [WCAG 1.4.11 非文字對比](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)，AA：辨識操作、狀態及必要圖形的視覺資訊需對相鄰色至少 3:1。不是每一條裝飾分隔線／卡片邊框都需 3:1；若有其他充分可見的控制項辨識方式，不能僅因裝飾邊框淡就直接判整個控制項失敗。

## 方法與限制

讀取 [lib/theme-lab.ts](../lib/theme-lab.ts) 的 `BUILT_IN_THEME_PRESETS` 實際產生結果，包含 `paletteFromRgb` 自動加深後的色值，沒有誤用原始 RGB 宣告。以獨立 sRGB 相對亮度公式（分段點 0.04045）計算，半透明組合先疊在底色上，完整精度判定後才顯示小數。

來源：`getThemeContrastChecks` 的五項核心配對、[Button](../components/ui/Button.tsx)、[IconButton](../components/ui/IconButton.tsx)、[WorkspacePageHeader](../components/layout/WorkspacePageHeader.tsx)、[globals.css](../app/globals.css)、[DailyRevenueChart](../components/analytics/DailyRevenueChart.tsx) 及本輪涉及的共用分頁。複算腳本 `.codex-artifacts/audit-nine-theme-colors.ts`，完整結果 `nine-theme-wcag-audit.json`、日誌 `nine-theme-wcag-audit.log`。

這是來源與配對計算分析，沒有逐一套用九套主題在所有頁面／狀態取得瀏覽器像素，沒有完成色覺差異的使用者測試或全站 WCAG 稽核。涉及漸層／hover 的數字描述指定的合成條件，不能把模型風險直接當作所有位置的實測失敗。

## 1.4.1：是否只靠顏色傳達資訊

共用主要流程有正向基礎：市集狀態有「待繳費／已繳費／已結束」文字；分頁有標籤、可見選中框與字重差異；危險操作有刪除文字或圖示；照片設定有啟用／未啟用文字。這些線索不因換九套主題而消失，沒有要求使用者先記住「綠色代表哪個功能」。

但 `aria-selected` 或只有螢幕閱讀器可讀的名稱，不能單獨取代視覺上的非顏色線索。所有圖表、表單驗證、付款方式、同步／離線與唯讀畫面仍需逐項檢查。現行每日收入趨勢有日期、平均線標籤與可展開表格，是有用的備援；仍應核對柱形／平均線本身的必要對比與資訊等價。未使用中的舊 RevenueChart／CategoryPieChart 不作現行分析頁失敗的直接證據。

## 已確認的共用缺口

### 1. 主按鈕 hover 降低了對比

六套在正常主色按鈕上通過，hover 換成 88% 主色疊淺底後，白字降為約 3.61–4.40。剩餘三套為 4.70–5.12。這是共用互動樣式問題，不需要因此刪除六套主題。

### 2. 危險按鈕 hover 的九套配對都不足 4.5

`Button` 的 `bg-danger text-white` 在正常情況有足夠基礎，但 `hover:bg-danger/85` 疊卡片底後只有約 3.46–4.14。應檢查所有 danger variant 的實際使用位置，優先保護正常字級的刪除／確認文字。

### 3. 淺透明焦點外圈

`Button` 使用 `focus-visible:outline-none`，各 variant 的焦點外圈為主色 20%–35% 等低透明度；在只有外圈作為焦點區別的淺底情境，25% 配對只有約 1.36–1.46，35% 約 1.55–1.73，未達必要狀態指示的 3:1。不是每個 App 控制項都只有此種提示，不能把此結果擴大成所有控制項皆失敗。

### 4. 頁首檢查沒有包含真實疊色

目前只測白字對純主色／純輔色。實際頁首另有白色 18% 徑向光、半透明主色中段、`text-white/80` 小字、`bg-white/15`／`hover:bg-white/25` 操作底。

- 單純主色上再鋪 25% 白底的小字按鈕：九套約 2.86–3.81。
- 單純輔色上鋪 15% 白底：九套約 3.43–3.79；25% 白底約 2.89–3.14。
- 80% 白色小字對純主色：六套低於 4.5，三套通過。

這些是現有 CSS 存在的合成組合，需要依文字實際位置、漸層尺寸與字級驗收；大標題若達大字定義可用 3:1，不能拿 4.5 一律判大標失敗。固定灰底的主題實驗室自身預覽，也不能替代實際 App 頁首檢查。

### 5. 低頻資訊色與圖表

- `info` 對卡片底為約 2.99–4.35，九套都不適合直接當一般小字；JapaneseD 暖霧的約 2.9927 也不能四捨五入為 3 來通過重要圖示門檻。其目前用處包括 PWA 分享圖示及測試救援資訊；救援頁非正式版主流程，應分開追蹤。
- 目前正式分析頁使用的每日收入趨勢，40% 主色柱對白底約 1.67–1.90、40% 輔色平均線約 1.68–1.75。如果需要靠這些圖形判讀高度或平均線，對比不足；需配合可見標籤、線型／輪廓及表格驗證，不能只看填色。
- `warn` 等亮色作淡底／裝飾並不必須具備文字級對比。不可把所有黃色或淡色對白底低於 4.5 都視為違規，也不應為通過檢查把所有背景變深。

## 建議修正順序（尚未實作）

1. **共用 Button／IconButton 的 hover 與焦點**：使用不透明、較深的同色階，或改變邊框／陰影，避免以降低底色透明度造成白字對比下降。焦點採清楚實線／外框，按實際相鄰底色驗證。
2. **實際頁首組合**：小字與操作使用可保證對比的背景；漸層最亮處、白光、半透明文字、hover 都加入驗收，不只測兩個純色色塊。
3. **主題實驗室檢查範圍**：明確標為核心配色檢查，補入實際互動狀態與選中配對。自訂主題目前仍只依五項核心組合決定是否可保存，測試裡通過的九套選中配對沒有自動擴張自訂主題保存 gate。
4. **圖表／低頻資訊狀態**：補足必要圖形對比及文字備援，接著用九套主題逐頁檢查手機／桌面、鍵盤焦點與灰階辨識。全站 WCAG AA 尚需評估其他條文，本報告不作完整 AA 保證。

九套目前均可保留。相對較高的數值裕度只能幫助特定配對，不能單憑主色深淺把某套評為整體「最無障礙」。本輪沒有套用上述修正，也沒有要求使用者再執行 SQL 或改動正式設定。
