# 全功能提示與說明規劃：手機優先

日期：2026-10-25（Asia/Taipei）。狀態：**已開始分批實作**；本機已完成的範圍與尚待項目見[第一批實作紀錄](CONTEXTUAL_HELP_IMPLEMENTATION_2026_10_25.md)。下文保留完整設計與驗收目標，不代表每列都已完成。

本提案回應「兼顧畫面簡潔與良好使用者體驗，如何規劃每個功能的提示」。依[提示來源索引](APP_UI_COPY_INDEX.md)、目前程式、[UIUX 再評估](APP_UIUX_PLAN_REASSESSMENT_2026_10_25.md)整理；延續前輪已實作的手機動線與六項 UX 改善，不將它們重新列為未完成。

規劃建立時沒有更動畫面、文案、權限、保存／同步、數字算法、付費方案或雲端資料，也沒有檢視 Demo。後續使用者已授權開始實作；各範例與來源是否已調整，以實作紀錄及目前程式為準。來源索引包含候選、保留碼與 gate 分支，不能把全部紀錄數當成正式 App 同時展示的提示量。

2026-10-25 補充確認：使用者要求先判斷說明是否必要，功能或欄位已能清楚表達時省略多餘說明，再對確有需要的內容套用提示分層。以下「必要性審查」優先於逐功能表；不將所有舊文字搬進說明窗口，也不為每個欄位預留資訊按鈕。

## 一、要達成的使用體驗

2026-10-26 實作進度：已接續[登入、資料準備與保存狀態調整](LOGIN_SYNC_UX_IMPLEMENTATION_2026_10_26.md)，保留原權限／保存契約。這批本機回歸與瀏覽器操作證據分開記錄。

使用者進入一個功能時，應能直接辨識「目前在處理哪場／哪天、目前結果或狀態、下一步能做什麼」。需要補充理解時，從附近一個具體的入口找到說明；已熟悉功能的人可以持續操作，不必反覆閱讀教學。

收合後仍要保留會影響決策的資訊：金額定義、目前付款方式、未送出資料、繳費期限、篩選條件、權限限制、資料來源不完整，以及破壞性操作的後果。

這符合 [GOV.UK Details](https://design-system.service.gov.uk/components/details/) 的使用邊界：次要細節可依需求揭露，大多數使用者完成任務必需的資訊應保持可見。本產品採用這個原則，不直接照搬其視覺樣式。

### 先判斷是否需要這段說明

實作順序調整為「查必要性 → 刪除重複／無資訊內容 → 改善名稱與控制 → 縮短必要內容 → 決定顯示時機與形式」。一段話即使語意正確，也不代表值得占用畫面或另外增加說明入口。

逐句檢查四件事：

1. **是否增加目前標題、欄位、按鈕或結果沒有表達的資訊？** 如果只是重述「這裡可以新增商品」，而按鈕已叫「新增商品」，可省略。
2. **拿掉後，新使用者是否仍能正確操作與判讀？** 要從不熟悉系統的人觀察，不能只因開發者或熟悉的老闆覺得明顯就刪除。
3. **是否涉及容易猜錯的規則或後果？** 格式、可用範圍、未記錄與零元、私人／團隊可見、資料送達、金額口徑等，不能以欄位名稱簡單就推定全部清楚。
4. **需要長篇解釋的原因是否出在介面本身？** 先考慮用更準確名稱、單位、預覽、預設值與可辨識控制解決；不要持續添加教學去補不易理解的介面。

| 審查結果 | 處理方式 |
| --- | --- |
| 重複標籤、描述顯然動作、泛泛鼓勵或不影響任務 | 直接省略，不另存進 ⓘ，也不增加新的入口 |
| 名稱、單位或控制可以表達清楚 | 合併到標籤／選項／結果；必要文字與讀屏名稱仍保留 |
| 有額外資訊，但一句可理解 | 留一行短提示，不為短句額外增加開啟／關閉步驟 |
| 只有特定選項／狀態才相關 | 符合條件時就近出現，原因解除才移除 |
| 有價值但不是當下必需的規則、公式或範例 | 才使用具名 ⓘ、原地展開或說明面板 |
| 會影響當下金額、期限、保存、權限或不可逆後果 | 保留直接可見的核心資訊；可將詳細背景放次層 |

以下為規劃時來源核對後的審查候選；首批已採用的項目見實作紀錄：

| 目前來源中的文字／位置 | 初步判斷 | 提案與保留邊界 |
| --- | --- | --- |
| 「名稱、地點與日期是市集的核心資料。」— [MarketFormFields](../components/markets/MarketFormFields.tsx) | 可直接省略的候選 | 下方已明確列出欄位及必要標示；這句沒有增加填寫規則，不需要放進說明面板 |
| 「先完成銷售時一定會用到的資料。」— [ProductFormFields](../components/products/ProductFormFields.tsx) | 可直接省略的候選 | 「基本資料」與必要欄位已提供結構，不增加填寫條件 |
| 「例如：華山文創市集」「例如：手工陶杯」 | 可省略一般範例的候選 | 市集／商品名稱已清楚時不必另附範例或 ⓘ；名稱標籤及必要驗證保持 |
| 「可一次選擇多個不連續日期。」及「選擇一個或多個日期」 | 合併／縮短 | 優先用「市集日期（可複選）」及選取結果表達；若不連續選取仍不易發現，在日期選擇器中保留就近短提示，不要求先開說明 |
| 地點的地標／捷運旁／地址範例 | 有額外資訊，宜縮短 | 允許自由地標或地址未必可由「地點」看出，可評估「地標或地址皆可」；不能誤導使用者必須填完整郵寄地址 |
| 「預設不記錄，不影響正常開攤與收攤。」— [MarketCashPanel](../components/markets/MarketCashPanel.tsx) | 可合併到選填與預設選項 | 標題「選填」及「不記錄（預設）」若已能讓新使用者理解，可移除重複長句；需驗證不記錄仍能正常完成開收攤 |
| 「草稿已保存在這台裝置，尚未送達雲端。」 | 必須保留其語意 | 欄位名稱無法表達保存結果；可以集中／縮短，不能只剩「已保存」 |
| 「比較時假設沒有其他現金進出。」、來源不完整與暫估 | 必須保留必要前提 | 可縮成清楚的前提／狀態摘要，不能僅因金額欄位看似明確就隱藏判讀限制 |

省略額外說明不等於刪除欄位標籤、單位、必填／選填、目前選擇、結果、可辨識操作名稱或輔助使用者的讀屏標籤。必要格式也不能只藏在輸入後就消失的 placeholder。[GOV.UK 輸入元件指引](https://design-system.service.gov.uk/components/text-input/)建議保持清楚可見的標籤；[Fluent 資訊標籤指引](https://fluent2.microsoft.design/components/web/react/core/infolabel/usage/)也要求避免重複既有標籤資訊，並將任務必要內容直接呈現。

## 二、統一採用的提示形式

| 代號 | 形式 | 適用情況 | 結束／恢復規則 |
| --- | --- | --- | --- |
| A | 常駐的名稱、欄位標籤、短摘要 | 定位、選填／必填、金額意義、主要狀態與下一步 | 隨真實資料更新；不是使用者看過就隱藏 |
| B | 就近出現的條件提示 | 當前選項、缺漏、期限、權限或來源狀態需要補充 | 原因解除才移除；仍需處理的問題不設自動消失 |
| C | 具名的原地展開說明 | 短規則、範例、範圍、公式與次要保存資訊 | 使用者自行展開／收起；不因一般資料刷新重設 |
| D | 可點開的說明面板 | 較長的步驟、權限對照與多個計算範例 | 有明確關閉；回到原輸入與閱讀位置；必要內容不只放在面板內 |
| E | 簡短操作結果通知 | 已完成且畫面有持續結果可核對的一般操作 | 通知可消失，結果／狀態留在畫面；時長與讀屏行為另做實測 |
| F | 明確確認對話框 | 刪除、捨棄、分享或其他具有實際後果的操作 | 說清對象與後果，提供具名確認和取消；不能以關閉等同確認 |

先完成必要性審查，再對留下的內容安排 A～F。一般優先 A＋必要的 B，次要說明選 C 或 D。不是每個卡片都要具備六種形式，也不為每個文字加問號。成功訊息、載入狀態和需要使用者處理的錯誤不使用同一套消失規則。

補充說明優先採「ⓘ＋具體名稱」；驚嘆號用於需要注意／處理的狀態，不作通用說明符號。沒有必要補充內容的功能，不展示空的資訊入口。

短說明適合原地展開，讓使用者看著說明操作；較長內容才開說明面板。手機可採底部面板，但內容太長、鍵盤或放大字體使閱讀困難時，應允許擴展為完整畫面；電腦可用合適寬度的對話框，沿用同一份內容。

## 三、逐功能安排

各表中的「常態」表示預設可見資訊，「條件」表示只有符合狀態才出現，「說明入口」為次要內容的固定可發現位置。操作按鈕本身應保留，不隨說明一起收合。

各列的說明入口是內容候選，不代表全部都必須建立。經必要性審查可省略、可由標籤表達，或沒有足夠補充價值的內容，連同其說明入口一併省略；不得為套用一致樣式而新增原本不需要的文字。

| 資料／情況 | 可以表達的語意 | 不能省略的差別 |
| --- | --- | --- |
| 成交／互動等事件 | 依既有事件與同步結果說明已記錄、待同步或失敗 | 本機記錄成功不等同雲端已確認 |
| 私人心得／現金草稿 | 草稿在此裝置、尚未送出，或明確雲端保存確認 | 一般同步成功不代表這些草稿已送出 |
| 成交照片／封面 | 分別依選取、暫存、傳送、完成或失敗階段說明 | 成交成功、照片已選取與照片已送達是不同結果 |
| 現金比較來源 | 讀取時點、未確認來源、基準是否變動及差額判讀 | 盤點已保存不代表成交來源完整，差額為零不代表帳務全部核對 |
| 全站同步入口 | 目前可核對的同步範圍與待辦 | 不用一個全站綠燈代表所有資料類型都安全送達 |

相同狀態在一個編輯器內集中呈現，避免上方、底部、通知同時重複長文；必要的頁首概況與編輯器對象狀態可並存，因為作用範圍不同。精簡呈現不改 writer、不新增自動保存、不改 retry／同步／雲端重建流程。

### 4.2 文案結構

- 一般欄位用清楚名稱、必要單位與必填／選填，不預設每欄都加範例。範例確實能解釋不明顯格式／允許內容時才保留；必要指示就近可見，不單靠會消失的 placeholder，標籤不隨輸入消失。
- 錯誤用「出了什麼問題＋現在如何處理」，在受影響位置保留；多錯誤表單可有可跳至欄位的摘要。
- 按鈕說清動作，例如「儲存到雲端」「捨棄這份草稿」，避免僅寫「確定」而必須回讀大段文字。
- 說明入口用「差額怎麼算」「盤點範圍」「角色權限」，不要一律用「更多」或無名稱問號。
- 用「場次狀態」「今日營業」「繳費紀錄」「盤點增減」「現金差額」等準確詞彙，保留它們的意義差別。
- 一句話可以理解的內容直接寫清楚；不為了收合而把短句增加成一次點擊。

這些表單規則參考 [W3C 表單說明](https://www.w3.org/WAI/tutorials/forms/instructions/)及[通知指引](https://www.w3.org/WAI/tutorials/forms/notifications/)：欄位需要清楚標籤、相關指示，以及靠近問題並可理解的修正訊息。引用是設計依據，並非本提案已通過使用者測試。

### 4.3 視覺與手機操作

- 維持現有品牌色與卡片語言。一般說明少用外框／底色，靠標題、間距與字重呈現層次；警示色保留給確實需要處理的狀態。
- 視覺順序優先為「定位／結果→主要操作→當下必要狀態→次要說明」。金額／保存相關短狀態可貼近其對象或提交按鈕，不要求所有頁面固定同一位置。
- 不靠縮小文字、淡到難讀或固定卡高壓縮內容；允許長名稱、翻譯、錯誤與放大字體自然換行。
- 延續主要動作約 48px、一般觸控控制至少 44px 的專案目標；短文字入口也應有足夠點擊範圍。
- 簡短次要內容採一層原地展開；避免「更多→說明→分類→文章」才能理解當前操作。
- 長說明面板提供明確關閉、可閱讀捲動範圍及正確焦點返回；返回／關閉不清空已輸入資料、不切換保存日期、不新增歷史往返問題。
- 錯誤、警示與可點擊入口不只靠顏色區分；具備文字、焦點與適當讀屏關聯。一般載入／保存進度使用低干擾宣告，阻擋操作的錯誤才使用相符強度。
- 說明不依賴滑鼠 hover；桌機可提供補充 tooltip，但手機點擊、鍵盤與讀屏都能取得同等必要資訊。

### 4.4 首次使用、空狀態與說明的可恢復性

首次進入某功能，可提供一段可略過的短引導；初期以有需要的空狀態及就近說明為主，不先增加全站強制導覽。使用者關閉教學後仍有固定說明入口。

「已看過教學」只影響一般教學顯示，不得使新發生的未保存、期限、權限、金額或資料不完整提示消失。需要記憶偏好時再定義帳號／裝置／內容版本的作用範圍，透過既有平台邊界處理；不將「讀過」當成使用者已正確理解或同意後果。

不要單憑一次點入欄位就自動展開長說明，避免鍵盤彈出時內容跳動。格式要求與修正提示留在欄位附近，長範例由使用者主動打開。無資料、無搜尋結果、沒有資格、來源未載入是不同空狀態，要各自說明。

## 五、三個具體畫面示例

### 示例 A：現金紀錄的預設閱讀

```text
開／收攤現金  選填                 盤點說明
營業日期  10/25

開攤現金       收攤現金
未記錄         未記錄

[記錄現金]
```

有草稿時，新增「有本機草稿，尚未送出」及處理入口；來源有錯誤時直接出現。真正顯示盤點增減或銷售比較時，才依各狀態補充必要判讀。不是用一張極簡卡蓋過全部異常。

### 示例 B：心得編輯

```text
私人心得                         填寫靈感
秋日市集 · 10/25

[ 心得輸入區                         ]

草稿已保留在此裝置，尚未送出。
[儲存到雲端]           [先收起，保留草稿]
```

與已保存版本並存時，顯示正在編輯的對象與版本差別；衝突提供處理入口。「人潮、停車、主辦、天氣」等靈感放在可展開內容，不占每次編輯的主要位置。單場與整場總結仍分清楚。

### 示例 C：差額來源不完整

```text
現金差額（暫估）                       差額怎麼算
短少 NT$300

成交來源尚未確認，暫不能據此完成對帳。
[查看現有來源問題]      [重新讀取現金銷售]
```

只有來源問題可用既有資料解釋時，才提供相應內容；不為這個按鈕偷偷新增資料端點或明細能力。公式可展開，暫估與問題摘要持續留在數字旁。

## 六、實作切片與先後順序

| 階段 | 工作 | 完成條件 |
| --- | --- | --- |
| P0：必要性審查與小範圍原型 | 由來源清單選實際可達畫面；先標示省略、合併、縮短及保留理由，保留後才安排常駐／條件／展開／面板／通知／確認及觸發與解除。先做現金、心得與資格限制的對照原型 | 能指出哪些文字真正省略、哪些語意仍必須直接可見、哪些細節如何再找到；不宣稱所有候選都是可刪內容 |
| P1：保存與判讀優先 | 現金、現金比較、心得草稿、同步摘要、付款期限、團隊資格；先去重與對齊作用範圍，再調整呈現 | 未送出、錯誤、暫估、期限及權限仍一眼能辨；不得把不同保存契約整合成假成功 |
| P2：高頻操作與一般表單 | 今日、清單、新增／編輯、快速收款、商品、待辦、交接、照片操作；再處理固定安排／縣市預覽 | 常態任務不增加步驟；範例就近、選項相關才展開；批次與照片狀態後果清楚 |
| P3：複雜解讀與低頻內容 | 分析算法、報表、角色完整對照、方案詳情、設定與公開頁 | 方法按需取得，數值前提／資格／購買必需資訊仍可見；沿原角色與訂閱 gate |
| 每一切片的手機驗收 | 先比較代表任務，通過後才推廣到相鄰功能 | 入口、關閉／返回、狀態、鍵盤、字體放大與資料不變皆通過；不以減少文字高度單獨判定成功 |

這是建議順序，沒有把 P0～P3 自動視為已授權實作。既有六項 UX 的已完成部分保留，本輪提案集中在提示的分層、去重、觸發與呈現；涉及新增端點、保存策略、權限或方案的變更應另列切片。

## 七、驗收方式

### 7.1 必須完成的代表任務

1. 新使用者能建立市集、設定繳費期限並找到下一步；能分辨等待錄取與已繳費。
2. 熟悉的使用者能快速完成收款，且不開說明也能確認場次、日期、金額與付款方式。
3. 不記錄現金仍可正常開收攤；實際 0 元不會被當成沒記錄。
4. 使用者能說出盤點增減與現金銷售差額的差別；來源不完整或零差額不會被誤認為全面對帳完成。
5. 心得編輯者能辨認正在看的已保存內容與未送出草稿，知道如何送出；打開／關閉說明不遺失輸入。
6. 老闆能區分角色、關係狀態與 Team 資格；查看者不會以為自己可收款，資格暫無法確認不會被誤導為必須付費。
7. 批次修改者能在確認前指出變更對象與範圍；捨棄／刪除者知道影響哪份資料。
8. 照片處理者能分辨成交已完成、照片待補與照片已送達。
9. 使用者可在原功能一按找到相應的次要說明，關閉後仍在原操作位置；必要資訊本來就直接可見。

### 7.2 觀察與判準

記錄任務完成率、錯誤／誤解、尋找入口與閱讀所花時間、返回是否迷路、是否需要旁人提示，再看一般狀態首屏可操作內容與捲動量。點擊數、說明開啟率與文字高度作為輔助指標；說明開得少可能是夠清楚，也可能是找不到，需結合任務結果判讀。

不先承諾「所有頁面文字減少某個百分比」或「新手必定幾秒上手」。先取得代表任務基準，再比較原型與實作；常態高頻流程至少不新增確認／導覽步驟，任何精簡造成的誤解都必須修正。

### 7.3 裝置與例外狀態

以 360／390px 手機寬度優先，涵蓋長場次名稱、大字體、軟鍵盤、頁面捲動與說明返回；再確認平板／電腦的呈現與鍵盤操作。採用現有平台能力與 shared model，說明內容與顯示條件不放入 Web-only business logic。

依功能覆蓋初次／熟悉使用者、老闆／員工、空資料／有資料、保存成功／失敗、草稿與衝突、離線／恢復、資格不確定、來源不完整與期限例外。沒有支援的能力不因原型出現就當作已上線。

## 八、後續如何維護

原始文案及行號仍由 [提示索引](APP_UI_COPY_INDEX.md)管理。本提案是設計決策層，不手改 `docs/ui-copy` 的自動產物。

實作前可在每個切片建立小型對照表：來源 ID／檔案、原文、新文或去向、必要語意、形式 A～F、顯示／解除條件、說明入口、資料範圍、驗收任務。位置型 ID 可能隨修改改變，需同時記來源檔與文字，不能把它直接當穩定的 runtime key。

對照表先補上「是否必要、理由、省略／合併／縮短／保留的決策」。確定省略的文字不必再指定 A～F 或建立說明內容；避免盤點變成把每句話重新安置一次。

文案改完後重新產生來源索引；若涉及訂閱揭露或相關檔案責任，沿[訂閱索引](SUBSCRIPTION_FILE_INDEX.mk)同步維護。若未來需要共用提示元件，應先用少量代表頁面驗證，不一開始全站替換；內容、條件與資料作用範圍仍由各功能真實狀態決定。
