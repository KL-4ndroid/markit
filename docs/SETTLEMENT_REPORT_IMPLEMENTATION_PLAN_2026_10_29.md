日期：2026-10-29。狀態：**已開始第一批本機實作**；[實作與驗證進度](SETTLEMENT_REPORT_IMPLEMENTATION_PROGRESS_2026_10_29.md)區分已完成、讀取部分完成及待保存工作，以下各批次不代表全部已上線。

依據：[第二輪 UX 複評](SETTLEMENT_REPORT_SECOND_UX_REVIEW_2026_10_29.md)、[現有報告實作與驗證](SETTLEMENT_REPORT_FACTS_AND_UX_2026_10_29.md)、[跨平台規範](CROSS_PLATFORM_VIBE_CODING_GUARDRAILS.md)。

## 目標與完成定義

品牌主應能快速回答：本期記錄多少收入、依哪些已填成本估算結餘、哪些場次值得回顧、比較涵蓋哪些資料、缺漏資料要到哪裡補正。

完成這次改善，不代表完成正式會計、庫存預測、原生實機或全部訂閱上架工作。維持手機單欄閱讀、桌面可對照表格、網頁閱讀為主與 PDF 選用；保留現有方案、角色與報告使用權益。

核心成功條件：

1. 免費場次、確定零成本、確定零收入都有正確的表示方式，不需要虛構金額或成交。
2. 報告指出問題後，入口能帶到正確來源；完成保存、同步及重開後，狀態仍正確。
3. 同一範圍的單場／報告／PDF 能對照金額與確認狀態；跨期差異能解釋。
4. 部分資料完整時仍可使用，但不把局部合計冒充整期淨利或完整成長。
5. 畫面減少重複提示與無用途控制，重要的金額範圍與限制仍可見。

## 目前已確認的實作起點

- `lib/reporting/settlement-report-reading.ts`：報告分類、逐日分攤、完整度與期間比較。固定費必須大於零、收入日成本必須大於零才接受，是目前零值情境卡住的主因。
- `lib/reporting/settlement-report-navigation.ts`：期別、排序、展開筆數、指定場次與返回契約；目前來源入口只區分 performance／costs／journal，尚未指定需補正日期／成交。
- `components/reports/settlement/SettlementReportReader.tsx`：總覽、比較、卡片／表格、商品、說明與待確認事項。
- `components/reports/settlement/SettlementReportScreen.tsx`：權益、資料載入與報告組合。
- `components/markets/MarketDetailScreen.tsx`、`DailyRevenueStats.tsx`、`DealDetailModal.tsx`、`AddRevenueDialog.tsx`：落點、每日明細、編輯入口與補登。既有補登把空成本轉成 0，且只接受正收入／正成交數；不能用這條流程偽造零收入紀錄。
- `lib/analytics/market-financial-summary.ts`：單場既有費用與估計淨利公式，需與報告的資料可信度語意對齊。
- `types/db.ts` 與既有本機／雲端投影：確認狀態必須經正常保存、同步與重建取得，不能只保存在報告元件。

上述是計畫定位，實作前仍須追查實際 writer、投影、RPC 與既有編輯行為。UI 上存在編輯按鈕，不等於所有成本修正路徑均可正確保存。

## 批次 0：固定來源與驗收基線

工作：

- 逐項追查收入、每日成本、商品成交成本、攤位／設備費、抽成、零收入判定的實際保存與讀取來源。
- 核對原有成交編輯：成本可否單獨修正、是否影響庫存、成交數、照片關聯、每日投影與同步；優先沿用可靠的既有流程。
- 列出單場摘要、列表、分析入口、獨立報告與 PDF 的金額範圍；先分清整場與本期分攤，再處理差異。
- 以既有 A／B 合成場次及純 fixture 固定基線，不修改歷史營運資料來配合測試。
- 先檢查目前未提交變更，維持本次報告改善與 Demo／素材等其他工作分離。

產出：來源與差異對照表、待新增持久化欄位／事件或 RPC 的最小設計、每一個寫入的權限與更新副作用清單。此批不進行雲端資料變更。

## 批次 1：共用零值、完整度與金額範圍模型

設計方向：

- 區分未填／已明確填金額／已確認為零；負數、非數字與矛盾資料另列需核對，不混成未填。
- 固定場次費與每日銷售成本分開判讀。單一費用總額為正不等於每個可選費用都已確認；保持「依已記錄費用估算」語意。
- 手動收入空成本代表未知；明確填入 0 才能表達確定零成本。商品成本未知時，不從目前商品成本推造歷史成本。
- 增加每日營業結果的明確語意：未記錄、已有收入結果、已確認零收入、只有互動。零收入確認不建立成交、不增加成交數、不扣庫存、不新增照片工作。
- 確認狀態跟隨場次／日期／來源版本。相關費用、日期、成交或成本被改動時，重新判定受影響範圍；不因編輯無關備註就要求重複確認。
- 舊資料的數值與投影保留；沒有可證明的明確零值確認時維持未知，不批次把 0 轉成「已確認」。既有可用正數資料按可核對來源相容處理。
- 收入是否可靠、成本是否足夠、是否已到完整日期各自判讀，避免一個布林值控制全部指標。

實作邊界：優先抽出小型共用判讀模組，由報告與單場共用；不要讓計算依賴 React、瀏覽器儲存或 Next 路由。最終欄位與命名在批次 0 來源盤點後確定。

驗收：免費且每日成本完整的 1,000 元收入／200 元成本場次，可得 800 元估計淨利；未確認免費仍待確認。明確零收入且攤位費 100 元，結果為負 100 元，成交數為 0；只記互動不能被當成已確認零收入。

## 批次 2：持久化與補正閉環

介面：

- 場次費為零且尚未確認時，提供一次「確認本場攤位與設備費為零」；仍保留抽成的獨立來源與檢查。
- 每日／成交成本提供「尚未填寫」與「確定為 0 元」的區別。清楚說明是在修正既有資料，不能按補登再次增加同一筆收入。
- 在已到營業日、沒有銷售結果時，提供明確「確認當日零收入」；顯示確認日期，允許依既有安全編輯規則更正。
- 將提醒拆成「核對某日銷售成本」「確認攤位與設備費」「核對某日收入」。進入既有明細後定位到日期／來源，有明確返回報告入口。
- 保存中防重複提交；失敗保留表單與上下文，成功後刷新判讀；僅本機待同步時，清楚顯示狀態。

資料與權限：

- 經既有合法 writer／投影路徑保存；若欠缺安全的修正契約，另做最小追加事件或 RPC，保留來源 ID、日期及必要版本，不能直接改唯讀每日投影充當修正。
- 必要時新增最小遷移與唯讀驗證，編號以實作當下倉庫為準，本計畫不預占 migration 編號。
- 新確認／修正以老闆及現有權益限制為準，前後端均驗證 owner、日期歸屬與有效方案；不擴張員工讀成本／利潤或改資料權限。
- 驗證重試冪等、同步重播、跨裝置讀取、舊客戶端寫入相容性及刪改後狀態失效；依既有離線政策保存，不另開未授權的重建／清除快取流程。

完成條件：報告 → 正確日期／來源 → 保存 → 返回相同期別、排序及場次 → 對應提醒解除；重整及重新登入仍存在。拒絕越權與版本衝突時，不留下部分成功假象。

## 批次 3：跨頁一致與部分範圍成果

- 同一整場範圍採同一費用定義及確認狀態；單場原先顯示 21 元、報告待確認的情況，要能看見一致的缺漏原因。
- 完整資料顯示「估計淨利」；有缺漏時全期仍為「待確認」，次要提供「已確認 X 場估計淨利小計」，列出納入／未納入場數與來源明細。未提供合格場次時不顯示 0 元小計。
- 小計只包含收入日完整、成本足夠、資料無異常的場次。範圍缺漏不被推成零收入／零費用，也不當作兩期成長依據。
- 整場與本期部分日期合理不同時，標示「本期分攤／整場費用」；保持活動日期逐日均攤、分幣尾差及保證金排除規則。
- PDF 與網頁使用同一判讀結果、同一期別及截止日，避免匯出又回到較寬鬆的舊完整度規則。PDF 列數限制獨立揭露。

驗收：完整場次淨利 700 元、另一場未填時，全期待確認但可見一場小計 700 元。補完第二場後更新全期；跨 10/31–11/1 的 1,000 元費用兩期各 500，原場次費用不改。

## 批次 4：比較、商品與提醒解讀

### 期間比較

- 保留前一個同長期間基準及實際起訖，這輪不新增多種比較模式。
- 對齊前期／本期的收入、場數、場次紀錄日數與每場紀錄日平均；若兩場同一天，分母是兩個場次日，不暗示一個日曆日。
- 保留資料不足、進行中或異常時不推算增減的規則；可以查看各期已知資料，但不稱為完整成長比較。
- 不新增時薪、任意成長百分比或因果推論；基期為零不產生無限百分比。

### 商品涵蓋範圍

- 顯示有商品明細的收入金額與同期總收入，沒有商品明細時只顯示短狀態；不強迫補齊商品才可回顧收入。
- 保留「已記錄件數」排序；只有一種商品、第一名並列或資料僅部分涵蓋時，不產生完整熱銷／備貨結論。
- 庫存改為「目前庫存」；沒有可靠時間戳就不製造庫存日期。商品毛利現值估算留在次要展開。
- 明細收入與總收入矛盾時顯示需核對，不把超過 100% 的數值硬截成 100%；總收入為零不做除法。

### 提醒與狀態

- 將需使用者補正的問題、正常營業進度、計算口徑分開；已完成跨期分攤不增加待辦數。
- 總場次使用互斥主要分類，部分日期缺漏作子狀態；例如「有紀錄 8 場，其中 1 場有日期待補」，避免重疊數字看似可直接相加。
- 未來場次以折疊數量呈現，不佔完整收入／淨利卡片；無需補正時隱藏空的提醒卡及其章節連結。

驗收：1 場 2 日對 2 場 4 日能清楚讀出量的差異；1,000 元收入只有 100 元商品明細時明列涵蓋量；並列商品不強選單一冠軍；跨期分攤不導致永久待確認。

## 批次 5：視覺與互動精簡

- 手機順序：期間 → 收入／淨利與範圍 → 必要補正摘要 → 可用的比較 → 市集 → 商品 → 成本／計算說明 → 次要 PDF。
- 待確認以簡短摘要呈現，明細仍在下方；完整資料時不插入無意義的警告。章節導航只包含存在且可見的內容。
- 維持單欄、兩欄數字對照，減少卡片內再套卡片、過大空白及重複導語。僅一場時隱藏排序，多場保留。
- 桌面對齊比較欄與數字、提供清楚表頭；不用把寬畫面塞進更多 KPI。長名稱換行，避免擠壓數字。
- 重要限制貼近數字，低頻口徑說明可展開；不用「!」取代所有必要標籤。
- 「本期值得注意」只留有數字、適用範圍的事實。沒有足夠素材就不產生通用建議；心得入口留在場次旁。
- 保持約 44px 觸控目標、鍵盤操作、焦點可見、展開語意與返回定位；手機鍵盤開啟後仍能看見保存／取消。

驗收：390×844、1024×768、1440×900 無橫向溢出，首屏可讀主要收入／淨利狀態；進場次與返回保留期別、排序、展開及定位，不只測 URL 字串。

## 批次 6：驗證與發布準備

| 類型 | 必驗案例 | 通過證據 |
| --- | --- | --- |
| 共用計算 | 明確零值／未知、零收入、部分日、跨期分幣、重複／異常資料 | 有意義的模型與來源不變測試 |
| 保存與權限 | 老闆正常保存、跨帳號拒絕、員工／免費越權拒絕、版本衝突、重試 | 本機及必要的隔離資料庫／RPC 測試，接著真實測試帳號保存 |
| 同步與相容 | 重開、重播、跨裝置、舊資料無確認欄位、舊版不覆寫新版確認 | 明確列出已驗與未驗範圍 |
| 報告數值 | 既有 A／B、700 元部分小計、800 元免費場次、兩期各 500 元 | 來源→單場→Web→PDF 金額及狀態對照 |
| 比較與商品 | 不同場次日數、基期 0、資料不足、10% 明細、並列、明細矛盾 | 不誤報完整成果／假成長 |
| UI 流程 | 深連結、補正、錯誤重試、返回、多場展開、三個尺寸 | 真實操作與截圖 |
| PDF | 實際產生、中文字、分頁、長名稱、部分資料提示 | 檔案渲染／預覽與下載，不能只檢查按鈕 |
| 建置 | 相關測試、修改檔 lint、Web build、mobile static checks | 確認本次結果；舊測試故障另列 |

執行順序為模型與寫入測試 → 真實保存與返回 → 跨尺寸 → PDF → 建置；失敗先修，再做受影響複驗。純文件建立階段不宣稱這些已通過。

發布準備：必要的最小遷移與驗證先就緒；確認雲端相容後才啟用需要新資料的介面。採可分批檢查的提交，保留其他工作；沒有使用者發布要求時不自行推送部署。部署後另核對版本及關鍵案例，不能把本機完成當線上完成。

## 資料與範圍保護

新增功能採最小追加，不重算歷史成交成本、不修改原有收入來通過測試、不批次確認舊零值、不清除照片／快取。測試盡量使用 fixture；既有 A／B 四筆補登及其四筆待補照片已有識別紀錄，不因本計畫自動刪除或補假照片。

不新增原生套件、Capacitor 專案、支付、備貨預測或會計科目；所有判讀、確認、驗證與同步契約保持平台中立。PDF／檔案能力沿用 `lib/platform`；如有新增裝置能力，依跨平台規範先設 port。

取消／延期損失、交通／人工成本與私人心得自動摘要，維持複評文件所列後續研究範圍，本輪不推造來源或擴大資料讀取。
