## 範圍與判讀方式

- 主環境：已登入的 `http://127.0.0.1:3000/`，目前測試版本的真實功能頁面、既有測試帳號，390 × 844 手機尺寸；含測試專用工具，不是正式發布產物驗收。
- 線上對照：已登入的 `https://markit-app-mocha.vercel.app/analytics`，只讀取 Free 分析的實際呈現。
- 兩個環境使用不同帳號；線上市集清單仍未顯示本輪新增的搜尋，因此不能假定線上與本機版本完全相同，也不能跨帳號比較總額。
- 不檢視、不修改 Demo；本輪不修改功能，不執行資料清除、修復、付款、方案模擬或角色變更。
- 分開標記「實際重現」「改善建議」「需追查」，不將開發模式編譯等待、瀏覽器自動化逾時直接判定為線上效能問題。

### 操作中的例外與資料邊界

原先以不改動既有紀錄為原則，但編輯測試市集的日期欄位時，按 Enter 意外觸發表單送出，
欄位未經人工修改。操作對象為 `[測試1020-02] 河岸週末市集`；這是一次真實儲存操作，不能把整輪稱為完全唯讀。
其後只使用點選開啟日期選擇器，並取消表單。

後續觀察到時間欄位錯誤紀錄，詳見 UX-01；沒有清理待處理資料、覆寫快取或執行自動修復。
未新增市集、商品、成交或補登收入，未切換報名／繳費狀態。
文字帶入功能使用的虛構原文已清除，沒有套用到市集或建立新市集；補登表單已關閉。

## 判斷

首頁、報名分類、搜尋與單場數字呈現已能支援主要用途。
接下來應優先改善資料可信度與操作連續性，再處理次要排版；目前證據不支持擴增更多首頁卡片。
本機資料健康通過不等於已驗證所有雲端寫入；同樣地，分析的資料不足不能被描述為營業趨勢。

## 優先問題與可重現步驟

### UX-01｜優先追查：編輯表單送出與同步成功回饋

**已觀察：** 開啟河岸週末市集編輯表單，在日期欄位按 Enter，沒有點選儲存，表單即進入送出狀態並關閉。
之後頁面曾顯示「同步中，1 筆待處理」。瀏覽器日誌從 2026-10-21 15:10:14 UTC 起，
多次出現 `22007 - invalid input syntax for type time: ""`，間隔約 30 秒。
後續帳號頁顯示已同步、0 筆；本機健康檢查也通過。

**來源核對：** `components/markets/EditMarketForm.tsx` 的 ownerUpdates 直接使用時間表單字串，
其中空白選填欄位可能為空字串；`lib/data-mappers.ts` 的轉換也不會把空字串排除。
這與錯誤相符，但本輪沒有核對雲端目標列或逐筆事件，不能宣稱已證明特定欄位未落地、資料丟失或整個同步失敗。

**影響：** 使用者可能只想開啟日期選擇，卻意外送出；而成功標示與持續錯誤之間缺少能理解的關係。

**下一步：** 先核對該次更新與雲端投影，再處理選填時間的空值契約、日期欄位 Enter 行為及成功／失敗訊息。
需要保留事件與失敗證據，不以清除資料或無限重試作為驗證方式。

### UX-02｜優先改善：資料不足仍描述營收持平

**線上實際重現：** 分析 → 最近 3 場，頁面同時顯示有效市集 0、營收 0、成交 0、可信度「資料不足」，
卻在營收比較顯示「大致持平／最近幾場營收大致持平，第一場為 $0，最近一場為 $0」。

**影響：** 無收入紀錄和營收沒有變化是不同情況，這種敘述容易被理解成經營結論。

**建議：** 資料不足時保留原始數字，改為「尚無足夠收入紀錄可比較」，提供補登／查看紀錄的下一步。
不要為了產出趨勢而把未有有效資料的樣本當作正常零營收。

**入口：** `lib/analytics/recent-market-revenue-preview.ts`、`components/analytics/RecentMarketRevenuePreview.tsx`。

### UX-03｜優先改善：查看成交明細的入口不夠明顯

**實際重現：** 星光設計補給站 → 回顧 → 每日表現，點日期卡片文字會打開三筆成交。
但畫面上沒有清楚的「查看 3 筆成交」標示，加號才是明確按鈕，其功能是補登收入。
成交列表又只先列時間、金額與付款圖示，需再點一筆才能知道商品。

**影響：** 想查「這場賣了什麼」的人不容易知道該點哪裡；想查既有紀錄也可能先進補登。

**建議：** 分開提供「查看 3 筆成交」與「補登收入」，以原生按鈕／連結表達。
每筆成交可增加一行商品摘要或品項數，減少為辨識紀錄而逐筆打開的次數。

### UX-04｜優先改善：文字帶入沒有明示未辨識欄位

本次只測一段明確的虛構文字，不代表完整解析正確率：

```text
市集名稱：秋日手作市集
活動日期：2026/10/24、2026/10/25
地點：台南文化廣場
營業時間：13:00–19:00
攤位費：每日 800 元
報到時間：12:00
```

**實際結果：** 產出日期、地點、報到時間、800 元／日四項；名稱與營業起訖沒有候選值，
也沒有清楚的缺漏清單。沒有套用、沒有建立市集，測試原文已清除。

**建議：** 先顯示「已辨識／仍需手填」摘要，優先突出必填名稱缺漏；再逐步改善常見欄名與時間寫法的辨識。
保留目前由使用者勾選與確認、不自動覆蓋資料的流程。

### UX-05｜後續改善：商品搜尋與返回不連續

**實際重現：** 商品 → 搜尋「耳環」→ 金盞花黃銅耳環 → 返回商品列表，搜尋回到空白、重新列出六項。
相同操作在市集頁會保留「星光」。商品搜尋只剩一項時，頁籤仍顯示「全部 6」，沒有說明這是總目錄數。

**建議：** 商品頁保留搜尋、分類與位置，沿用市集頁的暫時介面狀態能力；結果數明示「找到 1 項／目錄共 6 項」，
或讓分類數字一致採用篩選後結果。

### UX-06｜後續改善：現場尚未開放缺少具體下一步

**實際重現：** 未來且待繳費市集 → 現場，只顯示「市集狀態或營業時間尚未符合現場記錄條件」。

**建議：** 依既有共用規則列出實際尚未滿足的條件與預定開放時間，並提供前往管理的明確入口。
本項不代表要放寬現場記錄時間或跳過報名狀態規則。

### UX-07｜後續改善：操作語意與文字一致性

- 月曆上／下月與成交詳情關閉圖示在可存取樹沒有名稱；補登的金額／成本／筆數欄位也沒有對應名稱。
  應補齊可存取名稱；本輪未使用真實 VoiceOver，不宣稱已完成輔助功能實機驗證。
- 清單使用「估計淨利」，詳情為「淨利潤」，單日卡為「利潤」；數字一致，但用語應說明是否為估計與計算口徑。
- 一般功能的方案錯誤／方案說明仍有 runtime gate 等工程詞。
  正式使用者先看到目前狀態與下一步，工程細節另行收合。
  救援頁的 IndexedDB、deal_closed 等測試用語不再列入正式版文案改善範圍。

## 本機環境阻礙：不能直接當成線上故障

本機分析與報表頁顯示「目前無法確認方案權限」，重新檢查一次後仍相同；方案頁也顯示「尚無可信方案來源」。
線上另一個帳號可以開啟 Free 分析，因此本輪只確認本機該帳號受阻，尚未判定是帳號資料、API 設定或版本差異。
沒有開啟本機方案模擬或繞過授權來完成驗收。

## 已有效的部分

- 手機首頁問候區與空狀態高度已收斂，報名提醒在近期安排之前，沒有必要再加更多摘要卡。
- 待繳費摘要與清單一致，報名管理可以快速找到四個進度。
- 新增表單先呈現三項核心資料，其餘逐步展開，降低初次填寫負擔。
- 市集搜尋、分類及返回狀態連續；歷史營收與成交數在不同視圖一致。
- 成交照片到期會說明原因；補登明確區分不扣庫存，避免和正常成交混淆。
- 本輪未執行資料清除或修復；其畫面只作測試工具觀察，不視為正式版功能優點或待優化功能。

## 後續執行順序建議

1. 核對 UX-01 的時間值與同步落地結果，再修復必要的空值與回饋契約。
2. 修正零有效資料時的分析敘述，以及本機方案來源受阻的原因。
3. 加上可辨識的成交明細入口，改善文字帶入的缺漏摘要。
4. 統一商品／市集的返回行為與搜尋數量，再補強可存取名稱與正式功能文案，排除測試救援頁。
5. 正式發布時驗證測試救援入口／路由已撤下，並處理仍連向救援頁的清單與詳情錯誤入口；不進行救援頁改版。

此順序是本輪審查建議，尚未實作，不改變既有資料修復、同步寫入或原生上架的安全邊界。
後續分階段方案、驗收條件與對應檔案，以基礎流程紀錄中的 BW 計畫為準。
未新增平台能力或變更共用規則；本輪只新增此報告與本機證據，沒有因此重跑建置或新增鏡像式 UI 測試。
