# 訂閱價格版本與優惠活動後台需求

2026-10-26 三方案定案：[功能及價格基線](SUBSCRIPTION_FEATURE_TIERS_2026_10_26.md) 採免費、輕量（59／月、588／年）及高階（249／月、2490／年）。高階包含深入比較／分析、完整 PDF、成交照片與團隊，內含 owner＋3 位協作成員；圖片額度、擴充與舊權益對照待定。使用者再次確認後台必須保留訂閱價格設定，適用兩個付費方案的月／年價格、版本與排程。本文既有工作室首發優惠不能自動套用輕量版；後台及調價政策保留，runtime／商店未變。

日期：2026-10-23。

狀態：使用者已確認正式價格、首發優惠、後台可設定需求及未來調價政策（含既有月繳訂戶提前 60 天通知）；本文件記錄產品決策與實作順序，後台、動態價格讀取及商店發布尚未實作或啟用。

## 1. 已確認的產品決策

- 方案以免費版、輕量版與高階版為主；最新功能與內含席次見 [三方案規格](SUBSCRIPTION_FEATURE_TIERS_2026_10_26.md)。舊 Pro／Team 遷移對照仍需定義，不能直接將所有 Pro 帳號當成高階工作室。
- 起始牌價：輕量 NT$59／月、NT$588／年；高階 NT$249／月、NT$2,490／年。免費版維持免費；兩個付費方案的月／年價格均由未來後台按版本與生效排程管理，不永久寫死在 App。
- 高階版既有首發優惠：月繳前 3 個計費期每期 NT$199，第 4 期起 NT$249；年繳首年 NT$1,990，次年起 NT$2,490。金額為目標售價，須核對兩商店實際可用價格；不自動套用輕量版，跨方案首購資格及升級計費仍待定義。
- 領取期間為正式開放付費訂閱後 90 天；開始時間由伺服器記錄一次，不從文件日期或裝置時間起算。
- 首次付費品牌負責人適用；月繳／年繳優惠擇一，每位負責人限用一次，不疊加；員工不另買訂閱。
- 優惠與原價享有相同方案權益；取消後重訂不重置已使用的首購資格；輸入碼不直接授予權益。
- 未來可在營運後台建立不同時期的活動、優惠碼及價格版本，例行改動不需修改 App 原始碼或重新發布 App。新增不受現有模型支援的優惠類型仍可能需要開發。
- 未來售價變更按第 4 節已確認政策處理：新客依指定日期採新價，既有訂戶另安排通知與續訂調整；既有月繳漲價至少提前 60 天通知，年繳維持已付當年度價格，早期用戶回饋採有期限的保價。

本輪新方案的限期首購政策取代舊 Pro／Team 首發草案作為後續設計入口；不刪除歷史記錄，也不撤銷任何經證實已成立的交易承諾。不得將舊 `FERIA50` 或 Founder 條件自動套用到新方案。

## 2. 現況與限制

- 上述為本機來源核對，不代表遠端資料庫、正式收費或商店商品已啟用。

## 3. 營運後台功能範圍

此後台供 App 經營者使用，與品牌負責人／manager／staff 的日常工作畫面及角色分開。品牌負責人不得因擁有 Team 或工作室方案而取得營運權限。

| 模組 | 可設定內容 | 發布前需呈現 |
| --- | --- | --- |
| 方案與價格版本 | 方案、月／年週期、地區、幣別、目標價格、預定生效日 | 現價／新價、適用新客、舊客處理方式、各商店商品與價格對照 |
| 新客牌價 | 新購適用價格版本、開始生效時間、平台／地區／週期 | 哪些新購會適用；不得連帶改動既有訂戶 |
| 優惠到期後的價格 | 各活動的優惠結束條件、銜接價格版本與已揭露續訂條件 | 優惠何時結束、之後收多少；後續調價另有紀錄 |
| 舊客調價批次 | 適用訂戶群組、原價／新價、通知排程、預定續訂生效方式 | 逐戶影響、商店處理狀態、通知／同意條件及例外 |
| 訂戶價格與通知紀錄 | 查詢目前價格、優惠、下一次預定價格、變更原因與通知歷程 | 交易來源、資料時間；未知金額或未確認的時間不得推測 |
| 優惠活動 | 名稱、說明、領取起訖、適用方案／週期／地區、客群資格 | 優惠期、優惠後續訂條件、支援平台、與既有活動衝突 |
| 折扣內容 | 固定優惠價、折抵金額或百分比的設定意圖，以及優惠計費期數 | 各平台實際可售價格及期間；未支援的組合不可發布 |
| 優惠碼 | 活動對應、多個來源碼、啟停、總量／個人限制 | 各商店能否強制執行；無法保證的限制不得對外承諾 |
| 使用與成效 | 保留／已付款兌換／失敗／過期狀態、付費數、退款、續訂 | 統計以已驗證交易為準；標示資料時間與平台範圍 |
| 版本與操作紀錄 | 草稿複製、排程、停止新領取、操作者、理由及前後差異 | 影響範圍預覽與發布確認；保留歷史版本 |

活動結束日控制何時可新領取；優惠持續期控制成功購買後享有幾個計費期。停止新領取不取消已成立的優惠與訂閱。

固定優惠價、折抵、百分比是不同輸入模式；儲存時只能選一種，並落到經商店驗證的價格。百分比的換算與取整規則須明示，不能假裝任意數字都可由商店扣款。

已發布的經濟條件與資格改動採建立新活動版本；碼的啟停亦留下操作紀錄。不得原地改寫舊訂單價格、已取得的優惠期間或當時揭露內容。

## 4. 漲價與既有訂戶

以下為使用者已確認的產品政策，取代先前「60 天仍為建議值」的狀態；不代表已發布實際漲價或發放保價資格。

| 情況 | 已確認處理方式 |
| --- | --- |
| 首發優惠到期 | 按購買時揭露的條件，月繳前 3 期每期 NT$199，第 4 期起 NT$249；年繳首年 NT$1,990，次年起 NT$2,490。日後若另行調價，另走舊客調價流程。 |
| 未來正式價格上漲 | 新用戶從指定日期採新價；既有訂戶另外安排通知與續訂調整，不隨新客牌價發布直接改價。 |
| 既有月繳訂戶 | 至少提前 60 天通知，再於同時符合通知期限及商店要求的續訂日調整；若商店要求更長等待時間或用戶同意，需一併滿足。 |
| 既有年繳訂戶 | 當年度維持已付價格；通知後於符合條件的下一次年度續訂調整。若最近一次續訂尚不符合通知／商店要求，不得強制於該次調價。 |
| 特別回饋早期用戶 | 採明確期限的保價，記錄適用對象及結束日期。「再保留一年」是可設定的活動範例，尚未統一授予所有早期用戶或核定每次活動皆為一年。 |

例如未來將月費 249 改為 299，應建立新價格版本並設定新購生效日；299 只是操作示例，未批准任何漲價。

新購定價與舊客續訂遷移分成兩個操作。新客牌價發布只影響生效後符合條件的新購；既有訂戶按上述政策另行處理，這不構成永久鎖價承諾。舊客若要調價，必須另行預覽受影響訂戶、已承諾優惠、商店通知／同意條件與生效時間，再發布。

- 已付款的當期不追補差額；更改活動不重算既有交易。
- 年繳與月繳獨立設定，不從月費乘 12 推導實際年費。
- 訂閱需保留取得時的價格版本、活動版本、商店來源及已驗證的續訂資訊；不能每次打開 App 都套用最新牌價。
- 優惠結束接續哪個價格版本必須可追溯。日後漲價若影響這些訂戶，走舊客調價流程，不能在優惠結束時偷偷套用最新牌價。
- 已發布調價的撤回能力依商店狀態而定；後台不得宣稱所有發布都能立即撤銷。

### 4.1 新客牌價管理

- 依方案、計費週期、平台、地區及幣別管理新購價格版本與生效時間，保留歷次版本。
- 同一適用範圍的生效排程不得有模糊重疊；發布前預覽新購會取得哪個價格及商店映射。
- 新客牌價發布不自動產生舊客調價批次，也不改寫既有活動承諾的優惠後價格。

### 4.2 優惠到期後的價格管理

- 活動版本記錄優惠價、持續計費期數／結束條件、銜接價格版本及購買時揭露內容。
- 訂戶紀錄保存實際取得的活動版本、優惠進度與商店確認的優惠結束／續訂資訊；領取截止日與個人優惠結束時間分開。
- 優惠自然到期與另行漲價分開標示原因；更改公開牌價或停止活動，不自動重算訂戶已取得的條件。
- 日後若需調整銜接價格，必須建立對應的舊客調價批次，遵守已承諾條件及商店流程。

### 4.3 舊客調價批次管理

- 每批保留識別碼、建立者、原因、原價格／新價格版本、適用平台／地區／週期、納入條件、排除條件及預定生效方式。
- 發布前列出受影響訂戶及逐戶預估時程，排除不符合條件、受保價承諾限制或尚待確認的訂戶；發布時保存名單及決策版本，執行前重新檢查資格，避免使用過期預覽。
- 批次狀態至少包含草稿、待確認、已排程、處理中、部分成功、完成、失敗及已停止；保留逐戶商店結果，不能以批次日期代表所有人同日調價。
- 逐戶記錄通知排程、實際發送與結果、需否取得同意、已知同意狀態、商店確認生效時間及失敗原因。無法取得的狀態顯示未知。
- 發送請求成功、送達、閱讀及同意是不同狀態；不得將排程或 API 接受視為用戶已收到、已讀或已同意。商店通知與自家通知分開記錄來源。
- 既有月繳訂戶漲價的通知提前期至少為 60 天；後台可設定更長期限，不得設定較短期限。以伺服器時間、可稽核通知紀錄、逐戶續訂日及商店要求計算最早可調價時間，僅建立通知排程不算已通知。
- 任一通知期限、保價、商店等待或同意條件尚未滿足時，該訂戶不得調價；已付款當期不補收差額。年繳需於符合條件的年度續訂處理，不將月繳週期套到年繳。
- 重複執行不重複遷移或發送同一則通知；資格變更、取消訂閱及商店失敗需更新個別結果。停止批次後，已送出通知或已執行的商店操作仍保留，依商店能力處理後續。

### 4.4 訂戶價格與通知明細

營運者應能從單一訂戶明細回答「目前付多少、下一次預計付多少、何時變動、為什麼、已通知什麼」。至少顯示：

| 資料群組 | 必備內容 |
| --- | --- |
| 目前訂閱 | 方案、月／年週期、平台、地區、幣別、目前有效價格版本及優惠；區分最後實際扣款與目前續訂價格，避免將年費月均值當成扣款金額 |
| 未來變動 | 下一次預定金額、優惠結束時間、預定續訂／調價時間、變更原因、相關活動與調價批次；區分預估、已排程及商店確認 |
| 通知歷程 | 通知類型、來源／管道、內容版本、通知中的原價／新價與生效日、預定／實際發送時間、可驗證的送達／同意狀態及失敗紀錄 |
| 歷史及證據 | 價格與活動版本沿革、已驗證交易參照、商店最後同步時間、操作稽核；未知或過期資訊明確標示 |

所有查詢限營運管理員；Web 後台可採表格與逐戶時間線，但價格、活動、通知及批次狀態仍使用共用模型。通知紀錄不包含購買 token 或憑證。

### 4.5 早期用戶限期保價

- 每次回饋活動設定保價價格版本、適用對象、取得資格、開始與結束時間，保存逐戶取得紀錄，不以「早期用戶」文字標籤推測資格。
- 保價有效期間排除不符合保價承諾的調價；到期後仍需滿足通知與商店條件，再於適用續訂日調整，不在到期當天補收已付款期間差額。
- 後台明確顯示剩餘保價期間及到期後安排；修改新活動不縮短已成立的保價承諾。

## 5. Apple／Google 與自家後台的邊界

自家後台管理活動意圖、資格、版本、排程與稽核；實際可購價格、offer、購買與續訂以 Apple／Google 為準。後台輸入完成不等於商店已完成設定。

- Apple 訂閱 offer codes 可提供一定期間的折扣；既有 offer 不能任意原地修改，改資格需建立新 offer。自家活動版本要保存對應，不假定同一個商店碼可跨月／年商品共用。
- Google 訂閱 promo codes 主要是免費試用。金額折扣需對應 subscription offers，並核對其客群資格與購買方式。
- Google base plan 調價預設保留既有訂戶的舊價群組；Apple 也有保留舊價選項。既有訂戶漲價依地區及商店規則可能需通知或同意。
- 原生購買確認區使用商店回傳的實際價格、期間與續訂資訊；與活動意圖不符、資料過期或映射未驗證時，不提供該優惠購買入口。
- 商店外兌碼、跨裝置恢復、升降級、跨平台重複領取及總量限制均需單獨驗收。App 端隱藏入口不能證明商店端無法購買；無法強制的後台條件不得標成已支援。

平台狀態應分開顯示：草稿、待商店設定、待驗證、可排程、已生效、停止新領取、已結束、失敗。Apple 成功／Google 失敗時顯示個別狀態，不顯示籠統「全部發布成功」。

第一階段允許後台產出精確的商店設定清單並回填驗證證據。後續在官方 API 支援、憑證及驗收齊備後，自動建立／同步可支援項目；未支援項目提供明確人工步驟，不承諾零人工。

## 6. 共用規則與伺服器責任

- 共用模型涵蓋價格版本、活動版本、代碼、商店映射、資格判定、兌換狀態、交易來源及操作紀錄；商業規則不依賴瀏覽器 API。
- 商店讀取／購買／兌碼經 `lib/platform` 既有 IAP 邊界；伺服器管理 API 不能被打包入原生端或向客戶端暴露商店憑證。
- 所有管理寫入使用伺服器授權的營運管理員身分；未知權限、失效會話或離線均不能發布。不以隱藏按鈕代替伺服器權限。
- 資格與時間由伺服器判斷；未付款不消耗永久領取資格。若需配額保留，採限時保留、原子計數及明確到期，避免併發超領。
- 相同驗證交易只兌換／記帳一次；購買中斷後依交易恢復，付款成功後即使客戶端中斷也可完成核銷。
- 支援商店外兌碼時，以官方已驗證交易中的優惠資訊對帳，不能只依賴 App 預先建立的保留紀錄。
- 退款、撤銷及到期走既有訂閱生命週期，不由刪除活動來改權益。恢復購買不要求使用者再輸入優惠碼。
- 稽核記錄活動及碼的內部識別、操作者與結果；不記錄完整購買 token、秘密碼、商店憑證或用戶提供的原始碼值。公開活動碼與私密一次性碼的保存、匯出權限分開。

## 7. 實作順序與驗收

1. 依已確認三方案功能與席次基線，補齊圖片等額度、舊 Pro／Team 對照；保留舊交易及權益，不直接覆寫。新增支援輕量／高階各自月／年定價的共用價格／活動模型及案例測試；實際驗收待使用者恢復後進行。
2. 在既有不可變價格基礎上設計增量遷移與伺服器服務；擴充允許的新方案／活動類型、管理員授權及稽核。SQL 檔存在不代表雲端套用。
3. 完成營運後台草稿、預覽、版本、排程及平台狀態；分別建立新客牌價、優惠到期後價格、舊客調價批次，以及訂戶價格／通知明細，讓首發活動成為第一份可設定活動，而不是程式特例。
4. 將訂閱頁與資格查詢接到伺服器發布版本，搭配 fake store 驗證。未驗證商店映射維持不可購買。
5. 分平台接入商店設定／交易驗證及權益 writer，在 sandbox 驗證首購、優惠到期、取消重訂、恢復、退款、併發、舊客漲價與不同平台部分失敗。
6. 真實商店商品與發布證據完成後，啟用首發活動；Web ECPay 仍屬後續路線。

必要驗收：越權管理拒絕、資料版本衝突、過期碼、排程時間邊界、不疊加、跨平台重領、一次性交易核銷、優惠期與領取期分離、改牌價不改舊單、停止活動保留已成立權益，以及商店實際價格與揭露一致。
